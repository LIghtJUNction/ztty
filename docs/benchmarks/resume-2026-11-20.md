# 2026-11-20 核心处理阶段基准

本轮配对测量显示核心处理吞吐回退：ASCII、满历史 ASCII、SGR、Unicode 的中位数分别下降 **17.17%、10.19%、21.68%、79.05%**。初始核心堆内存增加 **15,360 B**；测量循环内的稳态分配次数保持为 0。热点归因仍在进行，本报告不把变化提前归因于拆库。

测量对象是 **zterm 的解析器与屏幕模型**，不包含 PTY、窗口、渲染、物理输入延迟或完整应用排名。ztty 0.5.0 仍是应用候选。本报告公开这次采集的全部 6 次进程运行及其原顺序，不把功能验收通过解释为性能改善。

证据入口：[完整配对记录](resume-2026-11-20/core-paired-6053.json) ·
[首次延后记录](resume-2026-11-20/core-paired-initial-deferred.json) ·
[路径脱敏清单](resume-2026-11-20/redaction.json)。

## 结果

A 为旧核心，B 为新核心。吞吐单位为 MiB/s，数值越大越快。
变化按 `(B 中位数 / A 中位数 - 1) × 100%` 计算；不是三轮百分比的平均值。

| 核心场景 | A：旧核心 | B：新核心 | 变化 |
| --- | ---: | ---: | ---: |
| ASCII | 305.179 | 252.769 | −17.17% |
| ASCII，历史容量 2,048 行且已预热 | 170.027 | 152.703 | −10.19% |
| SGR 与文本 | 160.360 | 125.587 | −21.68% |
| Unicode 固定混合文本 | 104.584 | 21.906 | −79.05% |

| 内存 / 分配观察 | A：旧核心 | B：新核心 | 变化 |
| --- | ---: | ---: | ---: |
| 初始核心堆字节 | 107,932 | 123,292 | +15,360 B（+14.23%） |
| `Cell` 字节数 | 28 | 32 | +4 B |
| 吞吐测量循环内的稳态分配次数 | 0 | 0 | 无变化 |

初始核心堆字节来自计数分配器在创建 `Terminal::new(120, 32, 2048)` 前后的存活字节差，
不是进程 RSS，也不是填满整个历史后的占用。稳态分配计数只覆盖预热后的四类吞吐测量循环，
不表示终端应用在启动或任意工作负载下都不分配内存。

## 全部配对运行

采集顺序为 **A/B、B/A、A/B**，每侧 3 次。下表保持执行顺序，没有删除较慢的运行。
六次进程均 exit 0，采集记录为 `ok=true, status=complete`。

| 顺序 | 轮次 / 核心 | ASCII | 满历史 ASCII | SGR | Unicode |
| --- | --- | ---: | ---: | ---: | ---: |
| 1 | 1 / A | 282.146 | 156.887 | 160.360 | 99.452 |
| 2 | 1 / B | 252.769 | 152.703 | 125.587 | 23.133 |
| 3 | 2 / B | 269.754 | 153.075 | 150.440 | 21.906 |
| 4 | 2 / A | 312.810 | 170.027 | 172.237 | 104.584 |
| 5 | 3 / A | 305.179 | 170.255 | 147.432 | 106.602 |
| 6 | 3 / B | 249.508 | 151.374 | 114.860 | 20.544 |

每轮四个吞吐场景的 B 都低于对应 A。这个结论描述本次固定样例和环境中的回退，
不建立不同硬件、真实终端工作负载或其他终端之间的总体性能排名。
JSON 还保留每次的 `edit_ns`、`burst_1024_ns`、分配计数、进程耗时及完整 host/PSI/swap 字段；
这些内部操作的纳秒数据不是按键到屏幕呈现的延迟。

## 工作负载与统计口径

[基准示例源码](https://github.com/LIghtJUNction/zterm/blob/13d5e2c74571d35cccd920b1204798211b70c79f/examples/benchmark.rs)
在旧、新两侧逐字一致，SHA-256：

```text
8551f815d1ca276154df9f2050a9039f0e9cd225da363137338d3c820ecc3624
```

屏幕尺寸为 120×32。每个输入串重复 32 次；ASCII 与 SGR 场景使用固定文本，
Unicode 场景包含中文、希腊文、日文、组合附加符和韩文。
每次 `feed` 后调用 `clear_dirty`，没有窗口或渲染器参与。

每个吞吐场景先预热 4,096 次，再测 7 批，每批执行 4,096 次 `feed`。
单个进程输出 7 批吞吐的中位数；本报告再取同侧 3 次进程输出的中位数。
吞吐按送入的字节数计算，包括控制序列和 UTF-8 字节。
ASCII 满历史场景将历史容量设为 2,048 行，其余吞吐场景为 0。

原始 JSON 保存了全部 6 次**进程级输出**；示例没有输出内部 7 批的逐批值。
因此这里没有虚构 21 批的合并分布、置信区间或统计显著性。
`edit_ns` 与 `burst_1024_ns` 保留各进程原有分位数，没有把这些分位数再当作全部操作样本合并。

## 运行环境与准入

采集于 **2026-11-20 00:23:30 UTC** 开始。两侧均通过 `taskset -c 23` 绑定同一逻辑 CPU；
实际继承的 **nice 为 −4**。执行者回执确认两侧未套用构建门禁的一 CPU cgroup quota；
原 JSON 未记录 `cpu.max`，这项范围说明来自执行者回执。
采集器在每次运行前后检查 host pressure，六次 `host_contention_after` 都为空。

本次记录的机器有 24 个逻辑 CPU；前后快照的 load1 范围为
**7.638671875–8.89453125**，最低 MemAvailable 为 **5,939,441,664 B**。
PSI 和 swap 数值完整保留在 JSON。准入通过表示未触发采集器阈值，不能理解为机器没有其他负载。

超过 24 个逻辑 CPU 一半的阈值 12，因此记录为 `deferred`，`runs=[]`。

## 复核与复现入口

[采集脚本原文](resume-2026-11-20/run-core-paired-6053.py)的 SHA-256 为
`2f155d3967ac1fadb6aa4dd0745f9a3a17c20b5b9ed6b5d078a61c7175a8a844`。
它核对两件二进制摘要，在每次采样前后运行压力检查，按 A/B、B/A、A/B 顺序执行，
并用三个进程输出重算中位数。压力判断来自
[固定采集源码中的工具](https://github.com/LIghtJUNction/ztty/blob/1a2f165983d7abff507c69b54c0c4ed225f49a45/tools/benchmark_terminals.py)。

复核者可以先用公开 JSON 重新计算表格，再按两个构建记录准备固定源码、编译器和 profile。
`WORKTREE` 表示整合工作树，`BASELINE_WORKTREE` 表示旧侧 detached 工作树，
`BASELINE_TARGET` 表示旧侧构建输出，`REPOSITORY` 表示外层仓库目录；它们都是显式路径占位符。

归档脚本应放回 `WORKTREE/artifacts/benchmark-final/run-core-paired-6053.py` 后使用；
它依赖相同根目录下的工具和冻结二进制，并拒绝覆盖既有测量文件。
重新测量应在新的记录目录/工作树中保存新结果和实际身份，保留本轮样本。

## 当前结论与下一步

本次核心样例存在明确回退，尤其是 Unicode 场景。零稳态分配没有抵消吞吐下降，
较小的根仓维护范围也不是性能改进的证据。
热点调查正在检查具体执行路径；在获得受控归因结果前，不把回退归因于目录拆分或某个依赖。

PTY 输出处理、窗口/GPU 呈现、物理输入延迟、完整应用内存与终端间对比仍待测。
后续修复或测量应记录新的固定来源与完整样本，并与本报告并列保留，不覆盖当前结果。
