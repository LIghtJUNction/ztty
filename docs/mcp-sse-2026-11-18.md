# ztty：MCP POST SSE 迭代验收

日期：2026-11-18，Asia/Taipei。验收平台：Linux x86_64，Rust 1.100.0。

## 交付结果

ztty 的 MCP HTTP 服务增加了可选的 POST SSE 响应。启动时指定 `--http-response sse`，客户端会先收到响应头和连接注释；等待终端输出期间，每五秒收到一条保活注释；请求完成后，服务发送一个完整的 JSON-RPC 结果事件并关闭响应流。默认 JSON 模式继续保留。

这轮从上次请求 ID 修复后的 `1bd658c` 继续开发，生产代码位于 [c0fee84](https://github.com/LIghtJUNction/ztty/commit/c0fee849446da748082db18f40e7c18d684faf29)，真实 PTY 测试、使用说明和本地检查入口位于 [dfb05e8](https://github.com/LIghtJUNction/ztty/commit/dfb05e8b3dd9b6e8fc4d05bfc95ec7daa9583d76)。这两个提交保持在同一条开发链上。

```sh
ztty mcp --transport http --host 127.0.0.1 --port 8732 --http-response sse
```

客户端继续连接 `http://127.0.0.1:8732/mcp`，并在 `Accept` 中同时声明 `application/json` 与 `text/event-stream`。`--http-response json` 显式选择原有模式。完整配置、权限和游标规则见 [会话与 MCP](sessions.md)。

## 为什么这样实现

输出等待已经能在没有新字节时停住读取，并允许其他请求继续输入、查询或取消。SSE 为这个等待过程提供可见的连接状态：HTTP 响应不必等到最终输出才开始，长等待期间也有小体积保活数据。每次读取仍返回一个有大小上限的输出页，调用者继续保存 `next_cursor` 和 `expected_session`。

实现沿用现有的单线程 `poll` 循环，没有增加工作线程或 Rust 依赖。连接只为当前响应保留发送队列。前一条注释未发送完时，下一条心跳不会加入队列；发送仍受十秒截止时间约束。心跳截止时间仅在发送队列为空时参与事件等待，避免因过期计时器反复唤醒循环。

响应沿用项目支持的 MCP 2025-11-25、2025-06-18 和 2025-03-26 版本。POST 的两种响应形式、通知状态及流结束语义参考 [MCP 2025-11-25 Streamable HTTP](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。

## 响应与资源规则

| 场景 | 本轮行为 |
| --- | --- |
| 初始化请求 | SSE 最终事件返回初始化结果；HTTP 响应头保留 `Mcp-Session-Id` |
| 等待终端输出 | 先返回 SSE 响应头及注释，约五秒保活一次，输出可用或超时后返回完整结果 |
| JSON-RPC 请求错误 | 通过同一 SSE 响应中的最终事件返回 |
| 已接受的通知 | HTTP 202，无响应体 |
| 鉴权、协议或请求格式错误 | 保留原有 HTTP 错误状态；适用时附 JSON 错误体 |
| 删除 HTTP 会话 | 结束该会话的等待连接，保留终端 PTY |
| 取消或等待连接断开 | 回收该请求的等待名额，保留终端进程 |
| 默认或显式 JSON 模式 | 保留原有 JSON 响应形式 |
| GET 请求 | HTTP 405；本轮没有新增主动订阅 |

HTTP 仍最多接收 64 个连接、64 个传输会话，其中正输出等待最多占 32 个连接。HTTP 负载、保留的 broker 数据及 SSE 帧共同使用现有 4 MiB 预算；解析对象、分配器容量、会话状态和内核缓冲属于额外内存成本。SSE 响应头已发送后若预算不足，服务关闭连接，避免把第二份 HTTP 响应塞进事件流。

响应没有事件 ID，也没有 `Last-Event-ID` 重放。客户端在读取中断后，用新的请求 ID、上次确认的字节游标和会话身份重新发起读取。终端输出仍按原有有界保留规则可读。取消或资源不足时，流可能缺少最终事件和 HTTP 终止块，客户端应将其识别为未完成请求。

七组 SSE 验收使用专属 broker、真实 PTY 和独立 HTTP 客户端。子进程通过文件握手控制输出时机，先验证响应头已送达，再允许其输出，因此能直接检查连接建立与最终结果的先后关系。接收端用 Python 标准库解码 HTTP 分块，独立检查 SSE 字段、单个最终事件和完整的零长度终止块。

验收覆盖初始化、Unicode 与控制字符、伪造 SSE 行仍作为 JSON 字符串交付、观察者权限、跨会话取消隔离、等值数字请求 ID、相邻大整数 ID、半关闭、等待超时、DELETE，以及 32 个等待连接全部断开后的全额复用。等待名额占满时，`ping` 和 `session_list` 仍可完成。Rust 测试还直接覆盖部分发送后追加最终结果、4 MiB 预算边界，以及开始 SSE 后超限时只关闭连接。
